# The API (draft, 0.x)

## Shape

- `include/neoj2k/neoj2k.h`: the C API. It is OpenJPEG 2.5.4's API with every name moved into neo-j2k's
  namespace (owner decision D5): `opj_*` becomes `nj2k_*`, `OPJ_*` becomes `NJ2K_*`, `JPWL_*` becomes
  `NJ2K_JPWL_*`, and the enum tags gain `NJ2K_`. The structures are the same, member for member, so their
  layout equals OpenJPEG's (`api_unit` asserts sizes and offsets). It compiles as C99 and as C++20.
- `include/neoj2k/neoj2k_openjpeg.h`: the compatibility header, generated by `tools/gen_compat.py` and
  checked in CI. It maps every OpenJPEG name onto neo-j2k's at compile time, so OpenJPEG code builds
  against neo-j2k unchanged and links `neoj2k`; `OPJ_STATIC` selects the static library as it does for
  OpenJPEG. `include/neoj2k/compat/` holds `openjpeg.h` and `opj_config.h` for code that includes those
  names. The tests compile their OpenJPEG request code against it (`tests/common/backend_neoj2k.cpp`).
- The surface D5 mirrors is the oracle's `openjpeg.h`: OpenJPEG 2.5.4 plus the fork's stage 1a additions,
  its decoder limits API (`opj_decoder_limits_t`, `opj_decoder_limits_init`, `opj_decoder_set_limits`,
  `OPJ_HAVE_DECODER_LIMITS`, `OPJ_DECODER_LIMITS_NONE`, `OPJ_DECODER_LIMITS_SL_TEXTURE`). Once the viewer
  sets the Second Life limits through it, switching to neo-j2k is a link change only if those calls map.
  Since stage 1b they map (`nj2k_decoder_limits*`, `NJ2K_DECODER_LIMITS_*`, `NJ2K_HAVE_DECODER_LIMITS`),
  with the same structure and the same Second Life numbers; `gen_compat.py --check` fails on any name of
  the oracle's header without a mapping.
- `include/neoj2k/neoj2k.hpp`: a header-only C++20 wrapper: owning handles, a memory reader over borrowed
  bytes (one stream at a time, its buffer sized to the bytes), everything `noexcept`, calling nothing but
  the C ABI.
- Extensions without an OpenJPEG counterpart keep their `nj2k_*` names (the compatibility header maps
  none of them): `nj2k_engine_string()` (a compile-time constant of at most 31 characters,
  `NJ2K_ENGINE_STRING_MAX`, safe before `main()`), `nj2k_cpu_supported()` (compiled for baseline x86-64),
  and stage 1b's: the OpenSim limit profile, statuses, the allocator hook, the reduce policy and the
  decoded dimensions (below).

## Limits (owner decision D10)

`nj2k_decoder_limits_init()` fills a profile, `nj2k_decoder_set_limits()` gives it to a decoder before
`nj2k_read_header()` (after it the call changes nothing and fails with `NJ2K_E_STATE`, as the fork's 1a). Every limit is checked from the headers before what it bounds is allocated; a field
of 0 is no limit, and a decoder without limits has none.

| Profile | Tiles | Components | Layers | Side at the decoded level | Working memory |
|---|---|---|---|---|---|
| `NJ2K_DECODER_LIMITS_SL_TEXTURE` (built in; the fork's 1a numbers) | 1,024 | 8 | 64 | 2,048 | 256 MiB |
| `NJ2K_DECODER_LIMITS_OPENSIM_TEXTURE` (module, `NJ2K_PROFILE_OPENSIM`, on by default) | 1,024 | 8 | 64 | 16,384 | 256 MiB |

The numbers come from the viewer's own size rules and from what each item costs, not from the cache
(plan audit A1, B2; `src/limit_profiles.h` gives the reasons). Every texture of the owner's viewer cache
passes the Second Life profile at every reduce level (`doc/testing.md`). Where they are checked:

- tiles and components: when SIZ is read, before anything per component is allocated (nothing per tile
  ever is: tile parameters exist only for tiles whose headers carry markers, plan S2);
- layers: as each COD is read, main header and tile-part headers;
- the side and the working memory: before decoding (`nj2k_get_decoded_dimensions()` runs the same
  check). The working memory is computed from the header: the decoded samples, the wavelet's lines and
  fixed scratch, and for the largest tile with the main header's coding its coefficients when there are
  several tiles, the code-block and precinct state of every resolution and the packet iterator's table
  (`decode_working_memory`, `src/header.cpp`; computed once per header and reduce factor). The memory a
  decode takes beyond the header stays within it for every corpus file at every reduce level
  (`decode_unit`, `test_memory_bound`);
- a tile whose own COD or COC changes its coding: its working memory again, with its own parameters,
  before the tile is allocated (`test_tile_memory_limit`);
- while decoding: what packets add per code-block (segments, data ranges) goes into the working arena,
  which never reserves more than `max_memory`, and a tile's decoded samples are refused when, with what
  the arena holds, they would pass it;
- the header state itself: the decoder's arena never reserves more than `max_memory`.

The codestream's own bytes are outside `max_memory`: the memory API reads the caller's bytes, and
`nj2k_decode()` holds the stream's (below).

The side is the decoded side, after the reduce factor, so `nj2k_read_header()` and
`nj2k_read_header_memory()` do not check it: a host reads a header at reduce 0 to learn the image's size,
then chooses a factor. It sizes its buffers only once `nj2k_get_decoded_dimensions()` (or its own checks)
accepts the decoded components; the decode fuzz target does exactly that (`fuzz/fuzz_decode.cpp`).

A profile unknown to the build (the OpenSim one with `NJ2K_PROFILE_OPENSIM=OFF`) sets no limits and makes
`nj2k_decoder_limits_init()` return false, as the fork's API does: check the result.

## Statuses

`nj2k_get_status(codec)` gives the outcome of the codec's last call that reports one, as
`nj2k_status_t`: `NJ2K_OK` (0) and `NJ2K_TRUNCATED` (1, stage 1c's partial decodes) are success; errors
are negative: `NJ2K_E_NEED_DATA`, `E_ARGUMENT`, `E_NOT_JPEG2000`, `E_HEADER`, `E_UNSUPPORTED`, `E_LIMIT`,
`E_NO_MEMORY`, `E_DATA`, `E_OUTPUT`, `E_STATE`. `nj2k_status_string()` describes each. Hosts treat an
unknown negative value as failure and an unknown positive one as success.

`NJ2K_E_NEED_DATA` means the bytes ended before what the call needs was complete (the main header and
the SOT marker after it, for `nj2k_read_header()`; the first tile-part header or the first packet of the
requested resolutions, for the decode): no damage was found, and with more bytes the call can succeed.
Every cut inside a main header gives it (`header_unit` reads every prefix of every generated file); a
host that holds every byte of the file already treats it as damage (plan audit D5).

## Allocator

`nj2k_create_decompress_with_allocator(format, allocator)` takes a host's `nj2k_allocator_t`
(`allocate` with an alignment, `release` with the size, `user`; not `malloc` and `free`, which debug and
leak-checking headers define as macros; `struct_size` first, as every growing structure of
neo-j2k's own). Everything the codec allocates for itself comes from it, the codec object included: one
block for the decoder and one arena block for an SL texture's header (2,312 bytes for a 32 x 32
texture). What the API hands to the caller comes from the C runtime's heap, as OpenJPEG's does, because
the functions that destroy it take no codec: the image of `nj2k_read_header()`, streams, the codestream
information. A failed allocation is `NJ2K_E_NO_MEMORY`, and the codec can still be destroyed
(`header_unit` fails every allocation of a header read in turn).

## Reduce policy and decoded dimensions

`nj2k_decoder_set_reduce_policy(codec, NJ2K_REDUCE_EXACT | NJ2K_REDUCE_CLAMP)`: under `EXACT` (the
default, OpenJPEG's behaviour) a reduce factor at or above a component's number of resolutions is refused
(`NJ2K_E_LIMIT`, at `nj2k_read_header()` when the factor came before it, else at
`nj2k_set_decoded_resolution_factor()`, which then changes nothing: fork audit S1); under `CLAMP` it is
lowered to the coarsest level the main header gives every component (plan W4), and the components'
`factor` says which level is used. A tile whose own COD or COC leaves a component no more resolutions
than the factor in effect has no level of the image's size, so it is refused (`NJ2K_E_LIMIT`) under
either policy, before anything of it is written (`decode_unit`, `test_clamp_tile_styles`). A viewer's
further rule (decode the coarsest level only while it stays small) stays the viewer's.

`nj2k_get_decoded_dimensions(codec, image)` sets each component's `factor`, `x0`, `y0`, `w` and `h` to
what the decode will deliver, before decoding, and runs the decode's limit checks: a host sizes its
buffers from it (plan P2a). OpenJPEG sizes the image differently when the factor comes before the header
(the header's rule) and after it (the decode's rule), which differ at odd origins; neo-j2k follows both, and
`header_unit` compares every generated file at every level in both orders with the oracle's decodes.

## What stage 1b implements

- Streams (`nj2k_stream_*`, file streams included) with OpenJPEG's semantics, except that a read function
  returning 0 ends the stream (OpenJPEG would call it for ever). A JP2 file is read only from a stream that
  gives its length (`nj2k_stream_set_user_data_length`; file streams do when the file has one): without
  it a box's own length is all there is to go by, so no box is read (`NJ2K_E_UNSUPPORTED`), as OpenJPEG
  reads none. A codestream's header needs no length: a marker segment holds at most 64 KiB.
- The decoder: creation (J2K and JP2/JPH formats; `NJ2K_CODEC_JPT` and the others give `NULL`), message
  handlers (a message is formatted only when a handler takes it), `nj2k_setup_decoder` (before the
  header), strict mode, limits, the reduce policy, `nj2k_read_header`, `nj2k_set_decoded_resolution_factor`
  (before the header the factor is kept and the call returns false, as OpenJPEG's, with `NJ2K_E_STATE`),
  `nj2k_set_decoded_components` (a refused selection keeps the earlier one, as OpenJPEG's; repeated calls
  reuse the same memory), `nj2k_get_decoded_dimensions`, `nj2k_get_cstr_info` and
  `nj2k_destroy_cstr_info`.
- The header model (`src/header.h`): the main header and the tile-part headers, read once into the
  arena, owning their bytes (PPM and PPT data included), with OpenJPEG's checks and messages; marker
  precedence and quantization counts as the standard has them (W7, W8, `doc/departures.md`); `Psot = 0`
  (W5); per-tile parameters only for tiles whose headers carry markers. The tile-part header reader is
  the library's, for stage 1c's decode loop.
- The JP2/JPH box reader (`src/jp2.h`): signature, file type, the JP2 header box (image header, bits per
  component, colour specification, palette, component mapping, channel definitions) and the codestream
  box; the image gets OpenJPEG's colour space and ICC profile.
- Still failing cleanly, with `NJ2K_E_UNSUPPORTED`: `nj2k_get_decoded_tile`, `nj2k_read_tile_header`,
  `nj2k_decode_tile_data` and `nj2k_set_decode_area` (decoding by tile and decode areas, a later stage);
  the encoder (6a). `nj2k_get_cstr_index` gives `NULL` (no codestream index is built, fork audit P5),
  `nj2k_dump_codec` prints nothing, `nj2k_codec_set_threads` is false (no threads of its own; stage 5's
  `nj2k_decoder_set_executor` takes the host's).

## What stage 1c implements

- `nj2k_decode` and `nj2k_end_decompress`: the decode of OpenJPEG 2.5.4 at the oracle's pin, the same
  image for every request of the reference tables, whole or cut, at every reduce level, in plain, strict
  and viewer mode (`doc/testing.md`). The stream's bytes are read into the codec's memory first (one
  buffer, kept for the next decode up to the retained bytes): up to the length the host gave, or a JP2
  file's codestream box end when the box gives its length (DP-15), taken at once when the length is
  known and grown by doubling when it is not. That buffer is the decode's input and lies outside
  `max_memory`. `nj2k_end_decompress` reads nothing more, also for a JP2 file (DP-13), returns true and
  leaves the decode's status as it was. The status after a decode is `NJ2K_OK`, or
  `NJ2K_TRUNCATED` when the bytes end before the codestream does (no EOC, a tile-part cut short, a tile
  missing): the image then holds what arrived. Packets that claim more bytes than their tile-part holds,
  in a codestream that is otherwise whole, decode as OpenJPEG decodes them, with its warning, and the
  status stays `NJ2K_OK`.
- The memory API, neo-j2k's own (no OpenJPEG name): `nj2k_read_header_memory` reads a codestream's (or
  JP2/JPH file's) header from the caller's bytes and keeps the header model while later calls bring the
  same main header (a byte comparison of the header, not a new parse); `nj2k_get_codestream_layout` gives
  the tile grid and the fewest resolutions without allocating; `nj2k_decode_memory` decodes into the
  caller's planes, `NJ2K_SAMPLE_I32`, `NJ2K_SAMPLE_U8` or `NJ2K_SAMPLE_U16` (the low bits, as an 8-bit copy
  of the image keeps them), with any row stride (negative for bottom-up) and sample stride (interleaved
  components), so the viewer's raw image is written in one pass. The caller's bytes are read only during
  the call, never written and never duplicated: data is read in place, apart from each code-block's bytes
  (copied into a padded buffer for the MQ decoder's sentinel), the tile-parts of a tile that has several
  (gathered in the working arena), the tile-part headers' marker segments and the main header (kept to
  know it again). The codec is the per-thread decoder: one per thread, kept by the caller. After a failed
  header read it takes the reduce factor for its next codestream as before a header
  (`nj2k_set_decoded_resolution_factor` keeps it and returns false), and its next header read starts
  afresh; after a failed decode it still holds the header, which checks a new factor at once. A
  component selection (`nj2k_set_decoded_components` after the header read) holds for the decodes of
  that header until the next `nj2k_read_header_memory` or a decode that reads another header; a plane
  for a component left out is refused (`NJ2K_E_OUTPUT`), and a selection decodes a JP2 file's
  codestream components as `nj2k_decode` does, without its palette or channel definitions.
  `nj2k_read_header_memory` does not check the decoded side or the working memory (above);
  `nj2k_get_decoded_dimensions` does, and `nj2k_decode_memory` refuses what they refuse before it
  writes anything.
- `nj2k_decoder_set_retained_bytes`: what the codec keeps between decodes (its working arenas, the Tier-1,
  wavelet and tile buffers, a stream's bytes), 8 MiB by default. A warmed-up codec makes no heap call to
  decode images up to 256 x 256 again, the same one or another (`decode_unit`, `test_zero_heap`: no
  allocator call and no `operator new` over the corpus, at reduce 0 and 1); a 1024 x 1024 decode needs more
  than 8 MiB and makes one allocation and one release each time.
- Under the OpenJPEG-shaped API the image (`nj2k_image_t` and its planes) still comes from the C runtime's
  heap, since `nj2k_image_destroy` takes no codec, as OpenJPEG's does. A stream's codestream is read into
  the codec whole before the decode, where OpenJPEG holds one tile's data at a time: for a multi-tile image
  the stream API peaks higher than OpenJPEG by the codestream's size (`doc/bench.md`); the memory API does
  not.

## Versions, and a host's cache

`nj2k_version()` (`opj_version()` through the compatibility header) is the library's release,
`NJ2K_VERSION_MAJOR.MINOR.PATCH`, and changes with every release; `OPJ_VERSION_*` stay 2.5.4, the API level
mirrored. `nj2k_engine_string()`, `"neo-j2k MAJOR.MINOR"`, names the decoder for logs and an About box.
Neither is a version of the decoded output. A host that keys a cache of decoded images on them keys it on
its own decoder-output version instead, bumped when the pixels can change (owner decision D13: once at the
fork's stage 1a hotfix, nothing at the switch). The viewer's texture cache keys on `getEngineInfo()`, which
holds `opj_version()` (`llimagej2coj.cpp`, `lltexturecache.cpp`): built against the compatibility header
unchanged, every neo-j2k release would purge every user's cache. The viewer switch (stage 8b) keys it on
the viewer's own output version.

## Stage 0

Implemented: the version and engine strings, the CPU check, the parameter defaults (byte-identical to
OpenJPEG's), the image functions (`nj2k_image_create`, `nj2k_image_tile_create`, `nj2k_image_destroy`,
`nj2k_image_data_alloc`, `nj2k_image_data_free`), `nj2k_get_num_cpus` and `nj2k_has_thread_support`
(false: the library starts no threads). `nj2k_set_MCT` stays false (Part 2). OpenJPEG declares
`opj_get_jp2_metadata` and `opj_get_jp2_index` but never defines them; neo-j2k defines both (they return
`NULL`). `nj2k_get_num_cpus` counts the logical processors of every processor group on Windows, where
OpenJPEG's `GetSystemInfo` counts the calling thread's group only (the two differ above 64 logical
processors); elsewhere both count the online processors.

## Where the per-thread decoder lives (settled in stage 1c)

Stage 1c took the second option below: a reusable-codec extension, the memory API above, which the viewer
calls from a decoder it keeps per thread (stage 8). The library keeps no thread-local or global state (the
global-state check stands). The options were:

- thread-local state inside the library behind the unchanged API, which the rules below and the
  global-state check (`tools/check_objects.py`: no `.tls`, `.tdata`, `.tbss`) rule out today: the check
  would be relaxed and a thread-exit design added;
- a reusable-codec extension that the viewer calls (the survey's viewer design, `api.md` section 2.4,
  keeps a `thread_local` decoder in a viewer-side `llimagej2cneo.cpp`);
- a host-owned pool behind the allocator hook (stage 1b's `nj2k_create_decompress_with_allocator` already
  routes the codec's own memory, the codec object included, to the host).

Under the OpenJPEG-shaped API the image (`nj2k_image_t` and its sample planes), the stream and its buffer
come from the C runtime's heap whatever the choice, since their destroy functions take no codec; a
zero-heap path needs the image and stream handled by the host or by the extension.

## Threads in one image (stage 5)

The library starts no thread and keeps no pool (plan T2, `performance.md` section 6). A host that wants
a large image decoded on several cores lends the codec its executor:

```c
typedef void (*nj2k_job_fn)(void *job_ctx, NJ2K_UINT32 index);
typedef struct nj2k_executor {
    NJ2K_SIZE_T struct_size;   /* sizeof(nj2k_executor_t) */
    NJ2K_UINT32 concurrency;   /* how many jobs the host runs at once, the calling thread included */
    void (*parallel_for)(void *user, NJ2K_UINT32 count, nj2k_job_fn job, void *job_ctx);
    void *user;
} nj2k_executor_t;
NJ2K_BOOL nj2k_decoder_set_executor(nj2k_codec_t *codec, const nj2k_executor_t *executor); /* NULL: none */
```

- `parallel_for` runs `job(job_ctx, i)` once for every `i < count`, on any threads in any order, the calling
  thread included, and returns when every job has returned. Jobs never wait for one another and never
  call into the codec or the executor, so an executor whose waiting caller runs jobs itself cannot
  deadlock, even with every worker busy or with many codecs sharing it: every decoder of a process can
  share the host's one scheduler, and nothing oversubscribes the cores (OpenJPEG's
  `opj_codec_set_threads` starts a pool per codec, and joins it when the codec is destroyed).
- `concurrency` says how the work is cut, never how many threads run: each stage is cut into that many
  parts (at most 64), Tier-1 into twice that many runs of code-blocks of about equal estimated cost (so
  one slow run is not the tail).
- Without an executor, with a concurrency below 2, and for every tile below 2^18 decoded samples over its
  components (a 512 x 512 grey or a 296 x 296 RGB tile), everything runs on the calling thread, with the
  operations of stages 1c-4: the codec makes no call to the executor (the tests check it), and the
  one-thread decodes cost what they cost before but for the reduced decodes of 64 and 128 px textures, 2-4 %
  slower through link-time code generation (`doc/bench.md`, stage 5). Inside a large tile,
  wavelet levels below 2^18 samples and output regions below 2^16 samples a component also stay on the
  calling thread.
- What runs through it: Tier-1 (the code-blocks, listed in OpenJPEG's order on the calling thread), the
  inverse wavelet's large levels (the horizontal lifting in bands of rows, the vertical lifting in
  stripes of whole groups of 16 columns, the rows put in order by the permutation's cycles), the colour
  transform, DC shift and copy into the caller's planes (bands of rows), and the clearing of large image
  planes a first tile does not cover. Not tiles in parallel: a tile's walk over its tile-parts and its
  packets (Tier-2) stays on the calling thread, as in OpenJPEG, and two tiles at once would hold two
  tiles' samples (the peak-memory gate).
- The same samples, status and messages in the same order for any executor and any concurrency: every
  part writes its own samples, with the operations of the one-thread code in the same order; nothing is
  summed across parts; and the one refusal of Tier-1 (bit-planes plus ROI shift at or above 31) is found
  while listing the code-blocks, the blocks before it decoded as one thread decodes them, its warning
  given after them.
- Memory: per part, a Tier-1 scratch (28 KiB and the largest code-block's bytes) and a wavelet line; per
  code-block of a threaded tile, 8 bytes (its estimated cost). It is kept between decodes like the rest of
  the codec's memory (`nj2k_decoder_set_retained_bytes`), outside the decoder limits' working-memory
  estimate (a small part of what the tile's layout keeps already); when it cannot be had, the tile is
  decoded on the calling thread, with the same outcome.
- `nj2k_codec_set_threads` stays false and `nj2k_has_thread_support` false: the library has no threads of
  its own. A host that has none either can use a small pool of its own (the tests' `tests/common/thread_pool.h`
  is one: workers started once and joined at its end, the caller running jobs while it waits).

## Builds and ABI

- `neoj2k_static` (`neoj2k_static.lib`, `libneoj2k.a`; define `NJ2K_STATIC` when linking it) and
  `neoj2k_shared` (`neoj2k.dll` with its import library `neoj2k.lib`; `libneoj2k.so`, soname
  `libneoj2k.so.0.0` while 0.x, the major version from 1.0). An installed package exports them as
  `neoj2k::static` and `neoj2k::shared`, the names a build tree gives them too.
- The shared library exports `nj2k_*` only: dllexport on Windows, a version script on Linux. `abi/exports.txt`
  lists the exports; `tools/check_exports.py --write-list abi/exports.txt` after an API change, which
  review then sees.
- No writable globals, no thread-local storage and no static initialisers in the library objects
  (`tools/check_objects.py`); no exceptions and no RTTI (the compiler enforces the status-code API).
- No floating-point contraction anywhere (`/fp:precise`, plus `-ffp-contract=off` for clang-cl; GCC and
  Clang `-ffp-contract=off -fno-fast-math`), so lossy output can be identical across compilers (D2).
- The instruction-set floor of neo-j2k's own code: x86-64-v3 (`/arch:AVX2`, `-march=x86-64-v3`), chosen at
  compile time; `NJ2K_SIMD=SCALAR` builds for baseline x86-64 (D8), and its test holds every object of the
  library to that.
- Hardening: `/guard:cf` and `/CETCOMPAT`; `-fcf-protection=full`, `_FORTIFY_SOURCE=2` when the toolchain
  does not set it, `-z relro -z now -z noexecstack`.
- The DLL keeps link-time code generation inside; the static library and the CPU-check objects never use
  it, in any configuration (`/GL` objects must not ship, and GCC LTO objects bind to one GCC), and the
  global-state test refuses LTO objects.
- The install ships `LICENSE`, `LICENSE.OpenJPEG` (OpenJPEG's licence and the notices of the code ported
  from it, which its licence asks binary distributions to carry) and `NOTICE.md` in
  `share/licenses/neoj2k`.
