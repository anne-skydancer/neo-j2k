# The API (draft, 0.x)

## Shape

- `include/neoj2k/neoj2k.h`: the C API. It is OpenJPEG 2.5.4's API with every name moved into neo-j2k's
  namespace (owner decision D5): `opj_*` becomes `nj2k_*`, `OPJ_*` becomes `NJ2K_*`, `JPWL_*` becomes
  `NJ2K_JPWL_*`, and the enum tags gain `NJ2K_`. The structures are the same, member for member, so their
  layout equals OpenJPEG's (`api_unit` asserts sizes and offsets). It compiles as C99 and as C++20.
- `include/neoj2k/neoj2k_openjpeg.h`: the compatibility header, generated by `tools/gen_compat.py` and
  checked in CI. It maps every OpenJPEG name onto neo-j2k's at compile time, so OpenJPEG code builds
  against neo-j2k unchanged and links `neoj2k`; `OPJ_STATIC` selects the static library as it does for
  OpenJPEG. `include/neoj2k/compat/` holds `openjpeg.h` and `opj_config.h` for code that includes those
  names. The tests compile their OpenJPEG request code against it (`tests/common/backend_neoj2k.cpp`).
- The surface D5 mirrors is the oracle's `openjpeg.h`: OpenJPEG 2.5.4 plus the fork's stage 1a additions,
  its decoder limits API (`opj_decoder_limits_t`, `opj_decoder_limits_init`, `opj_decoder_set_limits`,
  `OPJ_HAVE_DECODER_LIMITS`, `OPJ_DECODER_LIMITS_NONE`, `OPJ_DECODER_LIMITS_SL_TEXTURE`). Once the viewer
  sets the Second Life limits through it, switching to neo-j2k is a link change only if those calls map.
  Since stage 1b they map (`nj2k_decoder_limits*`, `NJ2K_DECODER_LIMITS_*`, `NJ2K_HAVE_DECODER_LIMITS`),
  with the same structure and the same Second Life numbers; `gen_compat.py --check` fails on any name of
  the oracle's header without a mapping.
- `include/neoj2k/neoj2k.hpp`: a header-only C++20 wrapper: owning handles, a memory reader over borrowed
  bytes (one stream at a time, its buffer sized to the bytes), everything `noexcept`, calling nothing but
  the C ABI.
- Extensions without an OpenJPEG counterpart keep their `nj2k_*` names (the compatibility header maps
  none of them): `nj2k_engine_string()` (a compile-time constant of at most 31 characters,
  `NJ2K_ENGINE_STRING_MAX`, safe before `main()`), `nj2k_cpu_supported()` (compiled for baseline x86-64),
  and stage 1b's: the OpenSim limit profile, statuses, the allocator hook, the reduce policy and the
  decoded dimensions (below).

## Limits (owner decision D10)

`nj2k_decoder_limits_init()` fills a profile, `nj2k_decoder_set_limits()` gives it to a decoder before
`nj2k_read_header()` (after it the call changes nothing and fails with `NJ2K_E_STATE`, as the fork's 1a). Every limit is checked from the headers before what it bounds is allocated; a field
of 0 is no limit, and a decoder without limits has none.

| Profile | Tiles | Components | Layers | Side at the decoded level | Working memory |
|---|---|---|---|---|---|
| `NJ2K_DECODER_LIMITS_SL_TEXTURE` (built in; the fork's 1a numbers) | 1,024 | 8 | 64 | 2,048 | 256 MiB |
| `NJ2K_DECODER_LIMITS_OPENSIM_TEXTURE` (module, `NJ2K_PROFILE_OPENSIM`, on by default) | 1,024 | 8 | 64 | 16,384 | 256 MiB |

The numbers come from the viewer's own size rules and from what each item costs, not from the cache
(plan audit A1, B2; `src/limit_profiles.h` gives the reasons). Every texture of the owner's viewer cache
passes the Second Life profile at every reduce level (`doc/testing.md`). Where they are checked:

- tiles and components: when SIZ is read, before anything per component is allocated (nothing per tile
  ever is: tile parameters exist only for tiles whose headers carry markers, plan S2);
- layers: as each COD is read, main header and tile-part headers;
- the side and the working memory: before decoding (`nj2k_get_decoded_dimensions()` runs the same
  check). The working memory is computed from the header: the decoded samples, the wavelet's lines and
  fixed scratch, and for the largest tile with the main header's coding its coefficients when there are
  several tiles, the code-block and precinct state of every resolution and the packet iterator's table
  (`decode_working_memory`, `src/header.cpp`; computed once per header and reduce factor). The memory a
  decode takes beyond the header stays within it for every corpus file at every reduce level
  (`decode_unit`, `test_memory_bound`);
- a tile whose own COD or COC changes its coding: its working memory again, with its own parameters,
  before the tile is allocated (`test_tile_memory_limit`);
- while decoding: what packets add per code-block (segments, data ranges) goes into the working arena,
  which never reserves more than `max_memory`, and a tile's decoded samples are refused when, with what
  the arena holds, they would pass it;
- the header state itself: the decoder's arena never reserves more than `max_memory`.

The codestream's own bytes are outside `max_memory`: the memory API reads the caller's bytes, and
`nj2k_decode()` holds the stream's (below).

The side is the decoded side, after the reduce factor, so `nj2k_read_header()` and
`nj2k_read_header_memory()` do not check it: a host reads a header at reduce 0 to learn the image's size,
then chooses a factor. It sizes its buffers only once `nj2k_get_decoded_dimensions()` (or its own checks)
accepts the decoded components; the decode fuzz target does exactly that (`fuzz/fuzz_decode.cpp`).

A profile unknown to the build (the OpenSim one with `NJ2K_PROFILE_OPENSIM=OFF`) sets no limits and makes
`nj2k_decoder_limits_init()` return false, as the fork's API does: check the result.

## Statuses

`nj2k_get_status(codec)` gives the outcome of the codec's last call that reports one, as
`nj2k_status_t`: `NJ2K_OK` (0) and `NJ2K_TRUNCATED` (1, stage 1c's partial decodes) are success; errors
are negative: `NJ2K_E_NEED_DATA`, `E_ARGUMENT`, `E_NOT_JPEG2000`, `E_HEADER`, `E_UNSUPPORTED`, `E_LIMIT`,
`E_NO_MEMORY`, `E_DATA`, `E_OUTPUT`, `E_STATE`. `nj2k_status_string()` describes each. Hosts treat an
unknown negative value as failure and an unknown positive one as success.

`NJ2K_E_NEED_DATA` means the bytes ended before what the call needs was complete (the main header and
the SOT marker after it, for `nj2k_read_header()`; the first tile-part header or the first packet of the
requested resolutions, for the decode): no damage was found, and with more bytes the call can succeed.
Every cut inside a main header gives it (`header_unit` reads every prefix of every generated file); a
host that holds every byte of the file already treats it as damage (plan audit D5).

## Allocator

`nj2k_create_decompress_with_allocator(format, allocator)` takes a host's `nj2k_allocator_t`
(`allocate` with an alignment, `release` with the size, `user`; not `malloc` and `free`, which debug and
leak-checking headers define as macros; `struct_size` first, as every growing structure of
neo-j2k's own). Everything the codec allocates for itself comes from it, the codec object included: one
block for the decoder and one arena block for an SL texture's header (2,312 bytes for a 32 x 32
texture). What the API hands to the caller comes from the C runtime's heap, as OpenJPEG's does, because
the functions that destroy it take no codec: the image of `nj2k_read_header()`, streams, the codestream
information. A failed allocation is `NJ2K_E_NO_MEMORY`, and the codec can still be destroyed
(`header_unit` fails every allocation of a header read in turn).

## Reduce policy and decoded dimensions

`nj2k_decoder_set_reduce_policy(codec, NJ2K_REDUCE_EXACT | NJ2K_REDUCE_CLAMP)`: under `EXACT` (the
default, OpenJPEG's behaviour) a reduce factor at or above a component's number of resolutions is refused
(`NJ2K_E_LIMIT`, at `nj2k_read_header()` when the factor came before it, else at
`nj2k_set_decoded_resolution_factor()`, which then changes nothing: fork audit S1); under `CLAMP` it is
lowered to the coarsest level the main header gives every component (plan W4), and the components'
`factor` says which level is used. A tile whose own COD or COC leaves a component no more resolutions
than the factor in effect has no level of the image's size, so it is refused (`NJ2K_E_LIMIT`) under
either policy, before anything of it is written (`decode_unit`, `test_clamp_tile_styles`). A viewer's
further rule (decode the coarsest level only while it stays small) stays the viewer's.

`nj2k_get_decoded_dimensions(codec, image)` sets each component's `factor`, `x0`, `y0`, `w` and `h` to
what the decode will deliver, before decoding, and runs the decode's limit checks: a host sizes its
buffers from it (plan P2a). OpenJPEG sizes the image differently when the factor comes before the header
(the header's rule) and after it (the decode's rule), which differ at odd origins; neo-j2k follows both, and
`header_unit` compares every generated file at every level in both orders with the oracle's decodes.

## What stage 1b implements

- Streams (`nj2k_stream_*`, file streams included) with OpenJPEG's semantics, except that a read function
  returning 0 ends the stream (OpenJPEG would call it for ever). A JP2 file is read only from a stream that
  gives its length (`nj2k_stream_set_user_data_length`; file streams do when the file has one): without
  it a box's own length is all there is to go by, so no box is read (`NJ2K_E_UNSUPPORTED`), as OpenJPEG
  reads none. A codestream's header needs no length: a marker segment holds at most 64 KiB.
- The decoder: creation (J2K and JP2/JPH formats; `NJ2K_CODEC_JPT` and the others give `NULL`), message
  handlers (a message is formatted only when a handler takes it), `nj2k_setup_decoder` (before the
  header), strict mode, limits, the reduce policy, `nj2k_read_header`, `nj2k_set_decoded_resolution_factor`
  (before the header the factor is kept and the call returns false, as OpenJPEG's, with `NJ2K_E_STATE`),
  `nj2k_set_decoded_components` (a refused selection keeps the earlier one, as OpenJPEG's; repeated calls
  reuse the same memory), `nj2k_get_decoded_dimensions`, `nj2k_get_cstr_info` and
  `nj2k_destroy_cstr_info`.
- The header model (`src/header.h`): the main header and the tile-part headers, read once into the
  arena, owning their bytes (PPM and PPT data included), with OpenJPEG's checks and messages; marker
  precedence and quantization counts as the standard has them (W7, W8, `doc/departures.md`); `Psot = 0`
  (W5); per-tile parameters only for tiles whose headers carry markers. The tile-part header reader is
  the library's, for stage 1c's decode loop.
- The JP2/JPH box reader (`src/jp2.h`): signature, file type, the JP2 header box (image header, bits per
  component, colour specification, palette, component mapping, channel definitions) and the codestream
  box; the image gets OpenJPEG's colour space and ICC profile.
- Still failing cleanly, with `NJ2K_E_UNSUPPORTED`: `nj2k_get_decoded_tile`, `nj2k_read_tile_header`,
  `nj2k_decode_tile_data` and `nj2k_set_decode_area` (decoding by tile and decode areas, a later stage).
  `nj2k_get_cstr_index` gives `NULL` (no codestream index is built, fork audit P5),
  `nj2k_dump_codec` prints nothing, `nj2k_codec_set_threads` is false (no threads of its own; a host calls
  stage 5's `nj2k_decoder_set_executor` to lend its own).

## What stage 1c implements

- `nj2k_decode` and `nj2k_end_decompress`: the decode of OpenJPEG 2.5.4 at the oracle's pin, the same
  image for every request of the reference tables, whole or cut, at every reduce level, in plain, strict
  and viewer mode (`doc/testing.md`). The stream's bytes are read into the codec's memory first (one
  buffer, kept for the next decode up to the retained bytes): up to the length the host gave, or a JP2
  file's codestream box end when the box gives its length (DP-15), taken at once when the length is
  known and grown by doubling when it is not. That buffer is the decode's input and lies outside
  `max_memory`. `nj2k_end_decompress` reads nothing more, also for a JP2 file (DP-13), returns true and
  leaves the decode's status as it was. The status after a decode is `NJ2K_OK`, or
  `NJ2K_TRUNCATED` when the bytes end before the codestream does (no EOC, a tile-part cut short, a tile
  missing): the image then holds what arrived. Packets that claim more bytes than their tile-part holds,
  in a codestream that is otherwise whole, decode as OpenJPEG decodes them, with its warning, and the
  status stays `NJ2K_OK`.
- The memory API, neo-j2k's own (no OpenJPEG name): `nj2k_read_header_memory` reads a codestream's (or
  JP2/JPH file's) header from the caller's bytes and keeps the header model while later calls bring the
  same main header (a byte comparison of the header, not a new parse); `nj2k_get_codestream_layout` gives
  the tile grid and the fewest resolutions without allocating; `nj2k_decode_memory` decodes into the
  caller's planes, `NJ2K_SAMPLE_I32`, `NJ2K_SAMPLE_U8` or `NJ2K_SAMPLE_U16` (the low bits, as an 8-bit copy
  of the image keeps them), with any row stride (negative for bottom-up) and sample stride (interleaved
  components), so the viewer's raw image is written in one pass. The caller's bytes are read only during
  the call, never written and never duplicated: data is read in place, apart from each code-block's bytes
  (copied into a padded buffer for the MQ decoder's sentinel), the tile-parts of a tile that has several
  (gathered in the working arena), the tile-part headers' marker segments and the main header (kept to
  know it again). The codec is the per-thread decoder: one per thread, kept by the caller. After a failed
  header read it takes the reduce factor for its next codestream as before a header
  (`nj2k_set_decoded_resolution_factor` keeps it and returns false), and its next header read starts
  afresh; after a failed decode it still holds the header, which checks a new factor at once. A
  component selection (`nj2k_set_decoded_components` after the header read) holds for the decodes of
  that header until the next `nj2k_read_header_memory` or a decode that reads another header; a plane
  for a component left out is refused (`NJ2K_E_OUTPUT`), and a selection decodes a JP2 file's
  codestream components as `nj2k_decode` does, without its palette or channel definitions.
  `nj2k_read_header_memory` does not check the decoded side or the working memory (above);
  `nj2k_get_decoded_dimensions` does, and `nj2k_decode_memory` refuses what they refuse before it
  writes anything.
- `nj2k_decoder_set_retained_bytes`: what the codec keeps between decodes (its working arenas, the Tier-1,
  wavelet and tile buffers, a stream's bytes), 8 MiB by default. A warmed-up codec makes no heap call to
  decode images up to 256 x 256 again, the same one or another (`decode_unit`, `test_zero_heap`: no
  allocator call and no `operator new` over the corpus, at reduce 0 and 1); a 1024 x 1024 decode needs more
  than 8 MiB and makes one allocation and one release each time.
- Under the OpenJPEG-shaped API the image (`nj2k_image_t` and its planes) still comes from the C runtime's
  heap, since `nj2k_image_destroy` takes no codec, as OpenJPEG's does. A stream's codestream is read into
  the codec whole before the decode, where OpenJPEG holds one tile's data at a time: for a multi-tile image
  the stream API peaks higher than OpenJPEG by the codestream's size (`doc/bench.md`); the memory API does
  not.
- **The host's floating-point environment does not reach the samples.** `nj2k_decode` and `nj2k_decode_memory`
  run under round to nearest-even with flush-to-zero and denormals-are-zero off (x86-64: the MXCSR's
  rounding-control, FZ and DAZ bits are set for the call and put back on every exit; the exception masks and
  flags are the caller's), once per call, whatever the calling thread had. The 9/7 samples are the same for a
  host that runs its threads rounding toward zero or flushing denormals (`fpenv_unit`).

## The encoder (stage 6a)

The core encoder writes what the Second Life viewer's upload encode writes (`JPEG2KEncode::encode`,
`llimagej2coj.cpp`, and the local bakes and snapshots, which call it), and its codestream is **byte for byte
OpenJPEG's** at the oracle's pin (owner decision D9: for good, no PCRD optimisation). It is OpenJPEG's encoder
API under the `nj2k_*` names: `nj2k_create_compress`, `nj2k_set_default_encoder_parameters`,
`nj2k_setup_encoder`, `nj2k_encoder_set_extra_options`, `nj2k_start_compress`, `nj2k_encode`,
`nj2k_end_compress`, with message handlers and `nj2k_destroy_codec` as for the decoder, and the compatibility
header maps the `opj_*` names. The statuses of `nj2k_get_status` apply (`NJ2K_E_UNSUPPORTED`, `NJ2K_E_LIMIT`,
`NJ2K_E_ARGUMENT`, `NJ2K_E_STATE`, `NJ2K_E_NO_MEMORY`, `NJ2K_E_OUTPUT` for a write function that fails).

### What it takes

| | The core encoder |
|---|---|
| Output | a J2K codestream (`NJ2K_CODEC_J2K`), one tile (no tile size) at the origin, one tile-part, SOC, SIZ, COD, QCD, COM, SOT, SOD, the packets, EOC |
| Image | 1 to 8 components, 8 bits unsigned, no subsampling, no offset, every component the image's size (`x1`, `y1`); 1 to 4,096 samples a side, at most 2^26 samples in all; an image of 1 to 3 samples a side encodes with a stream of any non-zero buffer, while the viewer-style zero-size stream guess for it is refused at `nj2k_stream_create(0)`, as in OpenJPEG |
| Wavelet | `irreversible` 0 (5/3, lossless: the samples come back exactly when the last layer's rate is 0 or at most 1) or any other value (9/7 with the standard's explicit step sizes) |
| Colour | `tcp_mct` 0 or 1; 1 needs three components or more and transforms the first three (RCT for 5/3, ICT for 9/7) |
| Layers | `tcp_numlayers` 0 to 100, rate allocation by distortion (`cp_disto_alloc` is not read): `tcp_rates[i]` is the compression ratio of layer i (a rate of 1 or less, or 0, is lossless; NaN, infinite and negative rates are taken as OpenJPEG takes them); 0 layers is one lossless layer, written back into the parameters. OpenJPEG's "rates should be strictly decreasing" warnings are not reproduced |
| Resolutions | `numresolution` 1 to 33 as OpenJPEG; the image must be at least 2^(n-1) samples a side (OpenJPEG's check, which neo-j2k makes at `nj2k_setup_encoder`, where the caller can lower `numresolution` and set up again), so at most 13 under the 4,096 limit |
| Size cap | `max_cs_size` as OpenJPEG: written back (the codestream size the last rate implies, saturating at `INT_MAX` where OpenJPEG's cast overflows at exactly 2^31), and, when it is above 0 (a cap, or the value an earlier setup wrote into the same parameters), the layers' rates lifted to the ratio it implies |
| Coding | RLCP (`prog_order` must be set to `NJ2K_RLCP`: the defaults are LRCP, which is refused), code-blocks 64 x 64, no precinct sizes (`csty` 0: one precinct a resolution), no mode switch (`mode` 0), no SOP, EPH, PLT or TLM, no ROI, no POC, no profile |
| Comment | `cp_comment`, up to 65,531 bytes (Lcom is 16 bits); none gives OpenJPEG's own (`Created by OpenJPEG version 2.5.4`, so that the bytes are the same) |
| Extra options | `PLT=NO`, `TLM=NO` and `GUARD_BITS=2` (what it does) |

Anything else of OpenJPEG's encoder belongs to the **j2k-extra** module and gives `NJ2K_E_UNSUPPORTED` from the
call that sees it (`nj2k_setup_encoder` for the parameters and the image, `nj2k_encoder_set_extra_options` for
an option), with a message naming it and nothing written to the stream: tiles and tile offsets, tile-parts,
precinct sizes, SOP and EPH markers, a progression order other than RLCP, POC, code-blocks of another size,
mode switches (BYPASS, RESET, TERMALL, vertically causal contexts, predictable termination, segmentation
symbols), a region of interest, profiles (cinema, IMF, broadcast, Part 2), custom colour transforms,
`max_comp_size`, fixed-layer and fixed-quality allocation, other precisions and signed
samples, subsampled or offset components, components of different sizes, `PLT=YES`, `TLM=YES` and other `GUARD_BITS` (an option that is none of these, or has another value, is `NJ2K_E_ARGUMENT`). JP2 and
JPT output (`nj2k_create_compress(NJ2K_CODEC_JP2)` returns `NULL`) belongs to the j2k-codestream module,
`nj2k_write_tile` and `nj2k_set_MCT` (writing by tile, Part 2 matrices) to j2k-tile. A request over a limit
(more than 8 components, 4,096 samples a side, 2^26 samples, 100 layers) gives `NJ2K_E_LIMIT`; an invalid one
(no components, an empty image, too many resolutions for the size, the colour transform of fewer than three
components, a comment of 65,532 bytes or more, a sample outside the 8-bit range, an image that is
not the one set up) `NJ2K_E_ARGUMENT`. Departures DP-16 to DP-19 (`doc/departures.md`) list where neo-j2k's
answer differs from OpenJPEG's on what OpenJPEG accepts. The limits (4,096 samples a side, 8 components,
2^26 samples, 100 layers, 8 bits) are the viewer's: OpenJPEG encodes larger images, and so will j2k-extra.

### How it runs

A call that the caller can mend (an invalid or unsupported setting, an image that does not fit its limits or
the settings, a sample out of range, a call out of order) is refused with its status and message and leaves the
encoder where it was, with nothing written to the stream: the caller fixes it and calls again. What it cannot
mend (out of memory, an output stream that fails, a tile that does not fit its buffer) ends the encoder: its
status says so and every later call but `nj2k_destroy_codec` fails.

`nj2k_setup_encoder` checks the parameters and the image and keeps the settings, `nj2k_start_compress` checks
the image against them, copies the sample planes (the caller keeps its own, unchanged, and may free them at
once, where OpenJPEG takes them and nulls the caller's pointers), writes the main header to the stream and
computes OpenJPEG's rate targets in bytes from the header's size (`opj_j2k_update_rates`, in the same float
arithmetic); `nj2k_encode` runs the tile, writes SOT, SOD and the packets in one write, `nj2k_end_compress` writes
EOC and flushes the stream. The stream needs a write function; skip and seek are never called (the tile-part's
length is known before it is written). A stream has a buffer, as in OpenJPEG (`nj2k_stream_create(0, ...)` returns
`NULL`, and so does a viewer-style stream of a zero size guess for an image under 4 samples a side); a write function
may take fewer bytes than it is given, the rest is offered again, and one that takes none fails the stream (DP-17). The tile's memory is released when `nj2k_encode` returns.

The stages are OpenJPEG's, ported with the same operations in the same order (`src/enc_dwt.cpp`,
`src/enc_t1.cpp`, `src/enc_t2.cpp`, `src/encode.cpp`; the MQ coder's states and the context tables are shared
with the decoder, `src/t1_tables.h`): the DC level shift, the colour transform, the forward wavelet
(OpenJPEG's lifting in its order, eight columns at a time for the vertical pass), the quantization of the 9/7
coefficients (`lrintf` to nearest even, as `opj_lrintf` on x86-64) and Tier-1 per code-block with the
distortion estimates in doubles, the layer allocation (the bisection on the slope threshold with a Tier-2
simulation for each step, `opj_tcd_rateallocate`), and Tier-2. Floating point follows the decoder's rules (D2):
no contraction, no fast-math, the 9/7 steps in the order of the SSE paths. The MQ coder's output is bounded
by its code-block's buffer (OpenJPEG writes without a bound, OD-4); the buffer OpenJPEG sizes for the codestream
(`m_encoded_tile_size`, about 1.4 times the raw size plus 500 bytes) is the room Tier-2 has, as in OpenJPEG, so an
image whose codestream outgrows it fails there as there (`NJ2K_E_LIMIT`, "Cannot encode tile"; ported, but no image of these settings has been found that reaches it), and an image whose
code-blocks do not fit the two guard bits of their band is refused (OD-6) as the pin refuses it.

The wavelet (one job a component) and Tier-1 (one job a code-block) use the host executor lent through
`nj2k_encoder_set_executor`. Images below 256 x 256 stay on the calling thread. Tier-1 runs bounded batches of at
most 64 code-blocks, one `EncT1` scratch per concurrent job; after each batch joins, its passes and bytes are committed
to the encoder arena in original code-block order. Thus a caller-supplied allocator is never called concurrently,
allocation failures occur at the same logical point, memory growth is bounded by the executor width, and codestream
bytes and diagnostics do not depend on scheduling. The library starts no thread.

`nj2k_start_compress` and `nj2k_encode` run under the default floating-point environment (round to
nearest-even, no flush-to-zero, no denormals-are-zero: the control bits are set for the call and put back on every
exit), so the quantization's `lrintf`, the 9/7 steps and the colour transform give OpenJPEG's bytes whatever environment
the calling thread had (`fpenv_unit`). Executor jobs run under it too, through the same job trampoline as the decoder's.

## Versions, and a host's cache

`nj2k_version()` (`opj_version()` through the compatibility header) is the library's release,
`NJ2K_VERSION_MAJOR.MINOR.PATCH`, and changes with every release; `OPJ_VERSION_*` stay 2.5.4, the API level
mirrored. `nj2k_engine_string()`, `"neo-j2k MAJOR.MINOR"`, names the decoder for logs and an About box.
Neither is a version of the decoded output. A host that keys a cache of decoded images on them keys it on
its own decoder-output version instead, bumped when the pixels can change (owner decision D13: once at the
fork's stage 1a hotfix, nothing at the switch). The viewer's texture cache keys on `getEngineInfo()`, which
holds `opj_version()` (`llimagej2coj.cpp`, `lltexturecache.cpp`): built against the compatibility header
unchanged, every neo-j2k release would purge every user's cache. The viewer switch (stage 8b) keys it on
the viewer's own output version.
The openjp2 module's `opj_version()` returns "nj2k", not a version: a viewer that caches on it refreshes its cache
once, when it first meets the module (the string differs from "2.5.4"), and not at a later neo-j2k release, which
decodes the same samples. The string is five characters at most, because Firestorm stores `OpenJPEG: 2.5.4, Runtime:
<it>` in a 32-byte field of its texture cache header (below).

## The openjp2 module

A viewer that talks to OpenJPEG through its own library file (`openjp2.dll`, `libopenjp2.so.7`) can take
neo-j2k without a line changed, recompiled or relinked: the module (`NJ2K_MODULE_OPENJP2`, `modules/openjp2`,
on in the presets, off by default as the other modules are) builds a shared library with OpenJPEG's name that
exports OpenJPEG's functions and holds neo-j2k. In practice that is a viewer built without Kakadu: the official
Firestorm releases link Kakadu statically and have no `openjp2.dll`, and the module is confirmed in a Firestorm
compiled without it (owner, 2026-11-22). It is an adapter between the calls a viewer makes and the
core's; the core is the same code as `neoj2k.dll` (the module links the static library) and never depends on it.

- **Exports.** Exactly the 55 functions of the oracle's `openjpeg.h` (OpenJPEG 2.5.4 plus the fork's decoder
  limits API), all `opj_*`, and no `nj2k_*` (`tools/check_openjp2.py`, test `openjp2_exports`). 49 of them call their
  neo-j2k twin with the same arguments: the structures have OpenJPEG's layout, so the call is the whole
  translation. `tools/gen_openjp2.py` writes them from `neoj2k.h` and fails if any function's return or parameter
  types differ from `openjpeg.h`'s (name for name, once `opj_` and `OPJ_` are mapped); a stale
  `modules/openjp2/opj_forward.inc` fails the test `openjp2_forwarders`.
- **It is neo-j2k, not OpenJPEG** (owner, 2026-11-21), under whatever name it is installed. The Windows library
  carries a version resource (`modules/openjp2/openjp2.rc.in`): product name `neo-j2k`, file description
  "neo-j2k JPEG 2000 codec, not OpenJPEG", comments "This is neo-j2k, not OpenJPEG. It is installed under the name
  openjp2.dll only because the viewer asks for that name.", so Explorer's Properties, Details say it for the file in a
  viewer's folder. `openjp2_exports` and the packager fail on a library without it. (`opj_version()` can say only
  "nj2k": see below.)
- **What the adapter does itself** (`modules/openjp2/openjp2.cpp`):
  - `opj_version()` returns `"nj2k"`. **Five characters at most**: Firestorm builds `OpenJPEG: %i.%i.%i, Runtime: %s`
    (`LLImageJ2COJ::getEngineInfo`, `llimagej2coj.cpp`) and stores it in the 32-byte `mEncoderVersion` field of its
    texture cache header (`sHeaderEncoderStringSize` in `lltexturecache.h`); a longer string stops the viewer with
    "Version string doesn't fit in header" (`lltexturecache.cpp`, a fatal error). OpenJPEG's own "2.5.4" is exactly
    five, and the text before it takes 26 of the 31 characters. v0.1.1 returned "Jpeg2000 through neo-j2k 0.1.1" and
    crashed Firestorm at start; `openjp2_unit` now builds Firestorm's string and checks that it fits. The About box
    reads `J2C Decoder Version: OpenJPEG: 2.5.4, Runtime: nj2k`; "OpenJPEG: 2.5.4" is the viewer's own compile-time
    text, and the full name and the version are in the file's version resource. The texture cache refreshes the first
    time a viewer meets the module (the string differs from "2.5.4") and not at later neo-j2k releases (the same
    samples), where a version in the string would purge it at every release.
  - `opj_has_thread_support()` is true, and `opj_codec_set_threads(codec, n)` starts the threads, which the core
    never does: the module is the host that lends the core an executor. A decoder or encoder gets a pool of its own,
    replaced by the next call and joined by `opj_destroy_codec`, as OpenJPEG's is (its threads are named
    `openjp2-worker`). The
    calling thread works while it waits, so `n` threads are `n - 1` workers and the caller (0 and 1 run on the
    caller), at most 64 (the most a stage is cut into); a negative count and no codec are refused. The samples
    and bytes are the same at every count (`openjp2_whole_threads`, `openjp2_unit`). The core calls the executor
    for tiles of 2^18 samples or more only, so a small texture decodes on the caller whatever was asked.
  - `opj_create_decompress` and `opj_create_compress` give `NULL` on a processor the library does not run on
    (`nj2k_cpu_supported()`, which the core's own callers check first; a viewer written for OpenJPEG does
    not). The adapter's own code is built for baseline x86-64 so that the check runs before any instruction of
    the core's does.
- **Where it differs from OpenJPEG** (as the core does, `doc/departures.md`): what the core leaves unsupported
  answers as it does there (`opj_get_cstr_index`, `opj_get_jp2_index` and `opj_get_jp2_metadata` give `NULL`,
  `opj_dump_codec` prints nothing, `opj_write_tile` and the tile-by-tile decoding functions and
  `opj_set_decode_area` fail, and `opj_create_compress(OPJ_CODEC_JP2)` gives `NULL`: the j2k-tile,
  j2k-codestream and j2k-extra modules'), and the decoder has no limits unless the host sets them
  (`opj_decoder_set_limits`).
- **Build.** `openjp2.dll` and `openjp2.lib` (the import library); `libopenjp2.so.2.5.4` with the soname
  `libopenjp2.so.7`, no symbol versions. It needs the C++ runtime (threads), as the core does.
  One module-wide writable global, the list of codecs that have a pool, under a lock.
- **Tests.** `openjp2_whole`, `openjp2_whole_threads` (4 threads), `openjp2_layers`, `openjp2_header` and, with the
  test data, `openjp2_conformance_differential` run the differential harness against the library loaded by path
  (`lib:`), the way a viewer loads it; `openjp2_unit` checks the version, the thread lifecycle (the pool's
  threads, named `openjp2-worker`, counted), decodes at 0 to 64 threads, decoders at once and the upload encode (`doc/testing.md`).
- **The release zip.** `tools/package_openjp2.py --library <openjp2.dll>` writes `neoj2k-viewer-<version>-win-x64.zip`:
  the library as `neoj2k-viewer.dll`, `INSTALL.md` (`modules/openjp2/INSTALL.md`: the swap, the check, the way back),
  `SHA256SUMS` and the licences, with fixed timestamps so the same library gives the same zip. **Nothing in the
  download says OpenJPEG or openjp2** (owner, 2026-11-21: a download named for OpenJPEG is written off by the people
  who would install it): the instructions rename the file to `openjp2.dll` when it goes into the viewer's folder,
  the one place where the viewer's own name for it matters. Build the library for it with
  `NJ2K_MSVC_STATIC_RUNTIME=ON` in the Release configuration: the DLL then imports `KERNEL32.dll` only, and the
  packager refuses a library that imports a C or C++ runtime, that does not export exactly `openjpeg.h`'s functions
  or that does not carry the release's version string.
- **Not built yet:** the installer that puts the file where a viewer's OpenJPEG is, and keeps the old one
  (owner, 2026-11-21).

## Stage 0

Implemented: the version and engine strings, the CPU check, the parameter defaults (byte-identical to
OpenJPEG's), the image functions (`nj2k_image_create`, `nj2k_image_tile_create`, `nj2k_image_destroy`,
`nj2k_image_data_alloc`, `nj2k_image_data_free`), `nj2k_get_num_cpus` and `nj2k_has_thread_support`
(false: the library starts no threads). `nj2k_set_MCT` stays false (Part 2). OpenJPEG declares
`opj_get_jp2_metadata` and `opj_get_jp2_index` but never defines them; neo-j2k defines both (they return
`NULL`). `nj2k_get_num_cpus` counts the logical processors of every processor group on Windows, where
OpenJPEG's `GetSystemInfo` counts the calling thread's group only (the two differ above 64 logical
processors); elsewhere both count the online processors.

## Where the per-thread decoder lives (settled in stage 1c)

Stage 1c took the second option below: a reusable-codec extension, the memory API above, which the viewer
calls from a decoder it keeps per thread (stage 8). The library keeps no thread-local or global state (the
global-state check stands). The options were:

- thread-local state inside the library behind the unchanged API, which the rules below and the
  global-state check (`tools/check_objects.py`: no `.tls`, `.tdata`, `.tbss`) rule out today: the check
  would be relaxed and a thread-exit design added;
- a reusable-codec extension that the viewer calls (the survey's viewer design, `api.md` section 2.4,
  keeps a `thread_local` decoder in a viewer-side `llimagej2cneo.cpp`);
- a host-owned pool behind the allocator hook (stage 1b's `nj2k_create_decompress_with_allocator` already
  routes the codec's own memory, the codec object included, to the host).

Under the OpenJPEG-shaped API the image (`nj2k_image_t` and its sample planes), the stream and its buffer
come from the C runtime's heap whatever the choice, since their destroy functions take no codec; a
zero-heap path needs the image and stream handled by the host or by the extension.

## Threads in one image

The library starts no thread and keeps no pool (plan T2, `performance.md` section 6). A host that wants
a large image decoded or encoded on several cores lends the codec its executor:

```c
typedef void (*nj2k_job_fn)(void *job_ctx, NJ2K_UINT32 index);
typedef struct nj2k_executor {
    NJ2K_SIZE_T struct_size;   /* sizeof(nj2k_executor_t) */
    NJ2K_UINT32 concurrency;   /* how many jobs the host runs at once, the calling thread included */
    void (*parallel_for)(void *user, NJ2K_UINT32 count, nj2k_job_fn job, void *job_ctx);
    void *user;
} nj2k_executor_t;
NJ2K_BOOL nj2k_decoder_set_executor(nj2k_codec_t *codec, const nj2k_executor_t *executor); /* NULL: none */
NJ2K_BOOL nj2k_encoder_set_executor(nj2k_codec_t *codec, const nj2k_executor_t *executor); /* NULL: none */
```

- `parallel_for` runs `job(job_ctx, i)` once for every `i < count`, on any threads in any order, the calling
  thread included, and returns when every job has returned. What the caller wrote before the call is seen
  by every job, and what every job wrote is seen by the caller once the call returns (each job's run
  happens before the return, as a mutex or a release/acquire pair gives it): the codec's stages rely on
  it, one stage reading what the parts of the one before wrote. Jobs never wait for one another and never
  call into the codec or the executor, so an executor whose waiting caller runs jobs itself cannot
  deadlock, even with every worker busy or with many codecs sharing it: every codec of a process can
  share the host's one scheduler, and nothing oversubscribes the cores (OpenJPEG's
  `opj_codec_set_threads` starts a pool per codec, and joins it when the codec is destroyed).
- `concurrency` says how the work is cut, never how many threads run: each stage is cut into that many
  parts (at most 64), Tier-1 into twice that many runs of code-blocks of about equal estimated cost (so
  one slow run is not the tail).
- Without an executor or with a concurrency below 2, everything runs on the calling thread, with the
  operations of stages 1c-4. With one, the codec calls it for two things only: the tiles (of 2^18 decoded
  samples or more in their largest component, 512 x 512), and the clearing of an
  image plane of 4 MiB or more (1,024 x 1,024 int32 samples) that the first tile written into it does not
  cover, which only a multi-tile image has, whatever its tiles' sizes. Everything else, small tiles
  included, runs on the calling thread and makes no call to the executor (the tests check it, on
  multi-tile images of small tiles too). The tile threshold and the clear threshold come from probes
  (`doc/bench.md`, stage 5: a fresh 1 MiB plane cleared in 8 bands took as long as on one thread, a 4 MiB
  one half as long); inside a large tile, wavelet levels below 2^18 samples and output regions below 2^16
  samples a component also stay on the calling thread, two estimates not probed on their own (they only
  apply inside a tile already split). The one-thread decodes run the operations they ran before; what
  their times do is in `doc/bench.md` (stage 5: within what moving `main`'s own code by a few bytes does,
  the one-thread Tier-1 walker has no counters: the parts' walker is a function of its own).
- **Busy or idle is the host's decision** (owner, 2026-11-20, superseding the image-level guard of the first
  stage-5 round, which kept images up to 2,048 x 2,048 on one thread whatever the host did). Lend the
  executor only when the host has idle cores, for example when its decode queue holds fewer jobs than it has
  workers; lend nothing when the queue is backed up. Never lend it to every decode on a saturated pool:
  splitting a decode there buys nothing and costs CPU (the saturated-host table in `doc/bench.md`). The
  library keeps no count of what else runs, so it cannot tell; with an executor lent it threads every tile
  of 2^18 samples or more, a 1,024 x 1,024 RGB texture included, and with none it never threads.
  A host that lends a high-concurrency executor may want to raise `nj2k_decoder_set_retained_bytes`: the
  default 8 MiB trim of what a decoder keeps may make it re-allocate its scratch on every decode of a
  512 x 512 texture at concurrency 64 (a performance effect only).
- What runs through it: Tier-1 (the code-blocks, listed in OpenJPEG's order on the calling thread and cut
  into contiguous runs of about equal estimated cost before anything is decoded), the
  inverse wavelet's large levels (the horizontal lifting in bands of rows, the vertical lifting in
  stripes of whole groups of 16 columns, the rows put in order by the permutation's cycles), the colour
  transform, DC shift and copy into the caller's planes (bands of rows), and the clearing of large image
  planes a first tile does not cover. Not tiles in parallel: a tile's walk over its tile-parts and its
  packets (Tier-2) stays on the calling thread, as in OpenJPEG, and two tiles at once would hold two
  tiles' samples (the peak-memory gate).
- **The jobs run under the default floating-point environment, whatever the host's worker threads keep.**
  Every job the codec hands to `parallel_for` sets round to nearest-even, no flush-to-zero and no
  denormals-are-zero when it starts, on whatever thread runs it, and puts the thread's control bits back when
  it ends (once per job, not per sample; the register is written only when it differs from the default). The
  output is independent of the host's floating-point environment: a host whose workers round toward zero (game,
  audio and physics threads often do) gets the samples of a decode on one thread in the default environment
  (`fpenv_unit`; before this, about half the 9/7 samples differed).
- The same samples, status and messages in the same order for any executor and any concurrency: every
  part writes its own samples, with the operations of the one-thread code in the same order; nothing is
  summed across parts; and the one refusal of Tier-1 (bit-planes plus ROI shift at or above 31) is found
  while listing the code-blocks, the blocks before it decoded as one thread decodes them, its warning
  given after them.
- Memory: per Tier-1 run, a scratch of 28 KiB with room for the largest code-block of that run (so the
  runs' room for coded bytes adds up to at most the tile's coded bytes, which the decoder holds already,
  whatever a stream declares); per part, a wavelet line; per code-block of a threaded tile, 8 bytes (its
  estimated cost). It is kept between decodes like the rest of the codec's memory
  (`nj2k_decoder_set_retained_bytes`), and it is outside the decoder limits' working-memory estimate, so
  that the limits refuse the same images with or without an executor. When the allocator refuses any of
  it, what was had for it is given back before the tile is decoded on the calling thread, so the tile has
  the room it would have had without an executor and the outcome is one thread's (the tests check it under
  capped allocators at every cap from below the least memory one thread decodes with to above what the
  threads need, on single- and multi-tile files). What a threaded tile kept is still held while the next
  tile is laid out, so under an allocator that refuses at exactly that margin, a later tile whose layout
  needs more than the earlier ones' could in principle be refused where one thread's would not; no tested
  file does that.
- The caller's planes (`nj2k_decode_memory`) are written from several threads: rows in bands, and a tile
  that decodes straight into them by code-blocks and stripes. `nj2k_decode_memory` checks only that a
  plane's samples fit their sample stride; with one thread, planes that share bytes (two planes over the
  same bytes, or rows closer than a row's samples reach) were harmless, the last write winning in a fixed
  order. With an executor, a decode into such planes runs on the calling thread, so it writes what one
  thread writes: planes are threaded only when no byte is in two samples (each plane's rows apart, and two
  planes apart or interleaved in common rows, as the viewer's interleaved image is).
- `nj2k_codec_set_threads` stays false and `nj2k_has_thread_support` false: the library has no threads of
  its own (plan T2). A caller written for OpenJPEG that checks `opj_codec_set_threads`'s result sees it
  fail and decodes on one thread; a host that wants threads calls `nj2k_decoder_set_executor` instead. A host that has none either can use a small pool of its own (the tests' `tests/common/thread_pool.h`
  is one: workers started once and joined at its end, the caller running jobs while it waits).

## Builds and ABI

- `neoj2k_static` (`neoj2k_static.lib`, `libneoj2k.a`; define `NJ2K_STATIC` when linking it) and
  `neoj2k_shared` (`neoj2k.dll` with its import library `neoj2k.lib`; `libneoj2k.so`, soname
  `libneoj2k.so.0.1` while 0.x, the major version from 1.0). An installed package exports them as
  `neoj2k::static` and `neoj2k::shared`, the names a build tree gives them too.
- The shared library exports `nj2k_*` only: dllexport on Windows, a version script on Linux. `abi/exports.txt`
  lists the exports; `tools/check_exports.py --write-list abi/exports.txt` after an API change, which
  review then sees.
- No writable globals, no thread-local storage and no static initialisers in the library objects
  (`tools/check_objects.py`); no exceptions and no RTTI (the compiler enforces the status-code API).
- No floating-point contraction anywhere (`/fp:precise`, plus `-ffp-contract=off` for clang-cl; GCC and
  Clang `-ffp-contract=off -fno-fast-math`), so lossy output can be identical across compilers (D2).
- The instruction-set floor of neo-j2k's own code: x86-64-v3 (`/arch:AVX2`, `-march=x86-64-v3`), chosen at
  compile time; `NJ2K_SIMD=SCALAR` builds for baseline x86-64 (D8), and its test holds every object of the
  library to that.
- Hardening: `/guard:cf` and `/CETCOMPAT`; `-fcf-protection=full`, `_FORTIFY_SOURCE=2` when the toolchain
  does not set it, `-z relro -z now -z noexecstack`.
- The DLL keeps link-time code generation inside; the static library and the CPU-check objects never use
  it, in any configuration (`/GL` objects must not ship, and GCC LTO objects bind to one GCC), and the
  global-state test refuses LTO objects.
- The install ships `LICENSE`, `LICENSE.OpenJPEG` (OpenJPEG's licence and the notices of the code ported
  from it, which its licence asks binary distributions to carry) and `NOTICE.md` in
  `share/licenses/neoj2k`.
